# Task: Redesign Canvas and Viewport Concept Type Safety (Canvas vs. Viewport Coordinates)

## Overview

Currently in `ofs_buf`, both viewport-relative coordinates (e.g. coordinates on the
visible screen `[0..viewport_height)`) and canvas-absolute coordinates (e.g. coordinates
on the continuous storage buffer `[0..total_canvas_lines)`) use the same type primitives
(`RowIndex`, `ColIndex`, `Pos`).

While these types protect against raw `usize` errors and unit mismatch (e.g. mixing up
`RowIndex` and `ColIndex`), they do not distinguish between **frame of reference**
(Viewport vs. Canvas). Consequently:

- Developers must rely on doc comments or parameter naming to know whether a method
  expects viewport-relative or canvas-absolute coordinates.
- It is possible to accidentally pass a canvas-absolute index into a viewport bounds check
  (like `Viewport::contains_row`).

### Proposed Solution

Introduce distinct type primitives for the two frames of reference, along with ergonomic
helper constructors:

1. **Viewport-Relative Types & Helpers**:
    - `ViewportRowIndex` & `vp_row(usize)`
    - `ViewportColIndex` & `vp_col(usize)`
    - `ViewportPos` & `vp_pos(col, row)`
2. **Canvas-Absolute Types & Helpers**:
    - `CanvasRowIndex` & `canvas_row(usize)`
    - `CanvasColIndex` & `canvas_col(usize)`
    - `CanvasPos` & `canvas_pos(col, row)`

### Architectural Answers to Feedback

1. **Location of New Types**:
    - Placed in a new domain submodule:
      **`tui/src/core/coordinates/canvas_viewport_coords/`** (`viewport_coords.rs` and
      `canvas_coords.rs`).
    - This follows the existing `coordinates/` taxonomy (alongside `buffer_coords/` and
      `vt_100_ansi_coords/`).
    - Re-exported via `crate::*` so they are available crate-wide across `ofs_buf`, VT-100
      performer operations, PTY multiplexer routers, and renderers.

2. **Decorator Pattern Rationale**:
    - The **Decorator Pattern** (`struct ViewportRowIndex(pub RowIndex)`) wraps the
      underlying primitive types (`RowIndex`, `ColIndex`, `Pos`) generated by
      `generate_index_type_impl!`.
    - This provides API boundary type safety so that it is semantically easy to follow
      what the code is supposed to do without being able to pass the wrong type in (even
      though the underlying value is identical).
    - Implementing `std::ops::Deref` for each wrapper forwards all arithmetic
      (`Add`/`Sub`), formatting (`Display`), bounds checking (`ViewportBoundsCheck`,
      `CursorBoundsCheck`), and helper methods directly to the underlying `RowIndex`,
      `ColIndex`, and `Pos` types with **zero boilerplate**!

3. **Decorator Newtypes & Ergonomic Constructors**:
    - `ViewportRowIndex(pub RowIndex)` & `vp_row(usize)`
    - `ViewportColIndex(pub ColIndex)` & `vp_col(usize)`
    - `ViewportPos(pub Pos)` & `vp_pos(col_val, row_val)`
    - `CanvasRowIndex(pub RowIndex)` & `canvas_row(usize)`
    - `CanvasColIndex(pub ColIndex)` & `canvas_col(usize)`
    - `CanvasPos(pub Pos)` & `canvas_pos(col_val, row_val)`
    - `Deref` / `DerefMut` and explicit `From` / `Into` traits allow seamless conversion
      to/from generic `RowIndex`, `ColIndex`, and `Pos`.
